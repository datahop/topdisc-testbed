# AWS run: 25 000 nodes, churn and unreachable nodes, registrars that drop late tickets (2026-10-25)

Runs `aws-25k-topdisc-cont-churn-ghosts` and `aws-25k-discv5-cont-churn-ghosts`, fork `v1.17.2-testbed.20`. The run directories are on the maintainer's machine. This page records why this run lost against discv5 and what it changed in the registration rules.

## Setup

The workload of the [final report](final-report/README.md): 25 000 nodes on 50 AWS hosts, the 100 largest chains of the 2026-09-18 crawl as topics, node sessions replayed from the [churn analysis](churn-analysis.md), one continuous 90 min search per node. On top of that, some node records point at unreachable ("ghost") nodes.

The registrar of this fork answered nothing to a REGTOPIC whose ticket was early, late or invalid, or whose ENR failed a check. Each advertiser sent its REGTOPICs for a topic through one sender, so a request to a dead registrar held every other request for that topic for the 700 ms response timeout.

## Results

| | TopDisc | discv5 |
|---|---:|---:|
| Recall, median over searchers | 35.7 % | 72.3 % |

- REGTOPIC timed out 38.7 % of the time. Only 20 % of these timeouts were at ghost nodes.
- In the node traces, 96 % of ticket retries reached the registrar after their 5 s window and got no answer. They were 76 % of all REGTOPIC timeouts (51 % in the 5 000-node run of the same workload).
- Retries that arrived inside the window were late, against its start, by 50 ms at the median and 3.8 s at the 99th percentile.
- Packet loss was about 0.1 %, and host CPU explains under 2 % of the timeouts.

Each timeout put a live registrar in the advertiser's failed set for 15 min and counted towards its eviction from the node table. The retry to the replacement registrar was late as well, so the losses fed each other. At 5 000 nodes the loop cleared after about 20 min; at 25 000 it did not.

## What changed

- A registrar answers every decoded REGTOPIC. A rejection is an answer and not a liveness failure, and an early ticket is returned unchanged.
- A retry up to 10 s after its window is credited with the wait it was scheduled to have.
- An advertiser sends through 4 concurrent senders per topic.

With these rules and the later search changes, the [final report](final-report/README.md) run on the same workload found 99.4 % of providers, against 71.3 % for discv5.
